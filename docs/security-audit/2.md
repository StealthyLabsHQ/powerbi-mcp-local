# Summary

Introduced bug: the commit added a new writing MCP tool but did not update the security tool category lists. The tool therefore bypasses readonly/write-deny enforcement.
This commit introduces pbi_export_correction_report, which generates content and writes it to output_path via out.write_text(). However, the tool name is not added to the WRITE_TOOLS set in src/security.py. Because tool_category() defaults unknown tools to read, SECURITY.validate_tool_call() does not block this file-writing operation when the server is started with --readonly or a policy denying write tools. A read-only MCP client can therefore cause local file creation/overwrite inside allowed directories. Due the centralized output_path extension rule this is especially likely to target .pbix paths, allowing corruption or replacement of Power BI report files despite an operator explicitly configuring read-only mode.

# Attack-path analysis

Final: high | Decider: model_decided | Matrix severity: medium | Policy adjusted: medium

## Rationale

The original high rating is justified, but not critical. Evidence shows a real authorization classification bug in the main runtime: the registered MCP tool writes via out.write_text(), is omitted from WRITE_TOOLS, and therefore falls through to category read, bypassing readonly/deny-write enforcement. The attack is reachable through normal MCP tool invocation when the server relies on --readonly or policy rather than profile pruning. The impact is materially security-relevant because it violates a policy boundary and permits unauthorized integrity/availability damage to local Power BI artifacts. Scope controls reduce severity below critical: writes are confined to allowed directories, symlinks are rejected, output_path is constrained to .pbix through centralized validation, default exposure is local/stdio or localhost SSE, and no RCE or secret disclosure is shown.

## Likelihood

medium - The bug is straightforward to trigger with one MCP tool call and was validated by an executable PoC. Exploitation still requires MCP tool-call access and a deployment relying on readonly/write-deny policy while leaving the default profile all or otherwise exposing the tool; the default transport is stdio/localhost rather than public internet.

## Impact

high - A caller limited to read-only semantics can create or overwrite local files within allowed directories, with output_path centrally constrained to .pbix. This can corrupt or replace Power BI report artifacts and defeats an explicit security boundary, but it does not provide arbitrary filesystem write, code execution, broad network compromise, or secret exfiltration.

## Assumptions

- An attacker can influence or issue MCP tool calls through an authorized/read-only MCP client, prompt-injected AI client, or an exposed SSE endpoint.
- The server is started with --readonly or a policy denying write tools, but not with --profile readonly/write pruning that removes tools not listed in READ_TOOLS/WRITE_TOOLS.
- The target output_path is inside the configured allowed base directory and has the centrally permitted .pbix suffix.
- MCP client/tool-call access to the local server
- readonly or deny-write policy relied on as the write-prevention boundary
- pbi_export_correction_report remains registered, such as the default --profile all
- attacker-controlled output_path within allowed directories

## Narrative

The finding is real and reachable in the main MCP server. src/server.py registers pbi_export_correction_report as an MCP tool and routes it through_run, which calls SECURITY.validate_tool_call before invoking the callback. The central security code blocks readonly only for tools categorized as write or destructive. pbi_export_correction_report is absent from WRITE_TOOLS, and tool_category() defaults unknown tools to read, so readonly and deny-write policy do not block it. The implementation in src/tools/quality.py resolves output_path, creates parent directories, and writes generated Markdown with write_text(). Path controls still restrict the destination to allowed directories and, through centralized output_path validation, to .pbix suffixes, so this is not arbitrary filesystem-wide write or RCE. However, it is an explicit authorization/policy bypass allowing a read-only MCP client to overwrite/corrupt local Power BI report files, which is a high-impact integrity violation in this project’s threat model.

## Controls

- --readonly runtime flag
- security_policy.json / PBI_MCP_SECURITY_POLICY allow_categories and deny_categories
- tool_category() central category gate
- allowed_base_dirs / PBI_MCP_ALLOWED_DIRS path confinement
- symlink rejection in resolve_local_path
- PBIX_FILE_EXTENSIONS validation for output_path
- SSE default bind to 127.0.0.1
- optional PBI_MCP_AUTH_TOKEN Bearer authentication
- --profile readonly tool pruning

## Blindspots

- Static review did not enumerate every generated wrapper or deployed client configuration.
- No cloud APIs were queried and no live external deployment exposure was assessed.
- Actual exploitability depends on whether operators use --profile readonly/write pruning, explicit enabled_tools, or default --profile all with readonly policy.
- Business impact depends on the sensitivity and operational importance of PBIX/PBIP files in the allowed directories.
