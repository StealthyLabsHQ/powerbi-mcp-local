# Summary

Introduced bug: the new policy engine fails closed only when `enabled_tools` is a non-empty list. An explicitly empty allowlist should mean no tools are enabled, but the implementation interprets it the same as the key being absent/null and allows every tool subject to other default category settings.
This commit introduced centralized security policy enforcement with an `enabled_tools` allowlist. However, `SecurityPolicy.from_mapping()` uses a truthiness check when converting the configured allowlist: `enabled_tools={...} if enabled else None`. If an operator configures `"enabled_tools": []` to disable all tools or temporarily lock down the server, the empty list is falsy and is converted to `None`. Later, `validate_tool_call()` only enforces the allowlist when `policy.enabled_tools is not None`, so the empty allowlist becomes no allowlist at all. As a result, all categories remain allowed by default, including destructive tools such as `pbi_delete_measure`, unless separately blocked by other policy fields.

## Report

Validated at commit efd08e3e1420cfc9dfa4db30ec30582c3a6cd7ca. Code review confirmed the policy parser reads `enabled = data.get("enabled_tools")` and then stores `enabled_tools={...} if enabled else None` at security.py:159-169, so an explicit empty list is collapsed to `None`. Enforcement only checks the allowlist when `policy.enabled_tools is not None` at security.py:265-269. The server calls this middleware before tool execution at server.py:78. `pbi_delete_measure` is classified as destructive via security.py:306-307, and the default documented categories allow destructive tools while `enabled_tools` defaults to `null` as an optional exact allowlist in SECURITY.md:214-216.

Direct PoC output: `empty allowlist policy.enabled_tools=None`; `empty allowlist pbi_delete_measure => ALLOWED`; `nonempty allowlist policy.enabled_tools={'pbi_connect'}`; `nonempty allowlist pbi_delete_measure => BLOCKED: Tool 'pbi_delete_measure' is not enabled by the active security policy.`; `VULNERABLE=yes`.

A non-interactive pdb trace confirmed the control flow: at security.py:159, `data` was `{'enabled_tools': []}`; after stepping, `enabled` was `[]` and `bool(enabled)` was `False`; after `from_mapping`, `policy.enabled_tools` was `None`; at validate_tool_call, the tool was `pbi_delete_measure`, category became `destructive`, the allowlist condition at line 268 was skipped, and execution continued to `VALIDATE_RESULT=ALLOWED`.

Crash/ASan/Valgrind were not applicable to this pure Python authorization logic flaw; valgrind and gdb were also not installed in the container. The debugger trace and direct PoC reliably reproduce the policy bypass.
