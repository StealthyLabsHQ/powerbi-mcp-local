# Summary

A security bug was introduced. The new fallback extraction code copies ZIP entries using attacker-controlled archive names without rejecting '..' path components or verifying that the resolved destination remains inside the extraction root.
The commit adds _extract_pbix_zip_natively() as a fallback when pbi-tools cannot extract a PBIX. It iterates ZIP entries whose names start with Report/StaticResources/ and writes each one to target / name. Because the ZIP member name is not normalized or checked after joining, an entry such as Report/StaticResources/../../../outside.txt passes the startswith check but resolves outside the intended extraction directory. This bypasses the repository's path allowlist validation, which only applies to the user-supplied pbix_path and extract_folder, not to paths embedded inside the PBIX archive. If an attacker can provide or influence a PBIX file and cause pbi_extract_report to run in an environment where this fallback is used, they can overwrite arbitrary files writable by the server process, potentially leading to local code execution through startup scripts/configuration files or corruption of user data.

## Report

Validated the finding against commit 8444f050cc47f683fc8c3792119dfdfa95eba0e4. Code review showed that src/tools/visuals.py:1278-1288 reads ZIP member names, accepts any member starting with "Report/StaticResources/", constructs `dest = target / name`, then calls `dest.parent.mkdir(...)` and `dest.write_bytes(...)` without canonicalizing the member path or checking that the resolved destination stays under `target`. The public entry point src/tools/visuals.py:1293-1325 invokes this fallback when pbi-tools is unavailable/lacks extract support. The user-supplied `pbix_path` and `extract_folder` are validated via src/security.py:543-574, but embedded ZIP member names are not. I created a PBIX ZIP containing a valid UTF-16-LE `Report/Layout` and a crafted entry `Report/StaticResources/../../../../../../tmp/pbi_mcp_zip_slip_owned.txt`. Running the public `pbi_extract_report_tool()` returned ok with `extraction_method: zip_native` and wrote `/tmp/pbi_mcp_zip_slip_owned.txt` with attacker-controlled content, outside the requested extraction folder. Reproduction output: `outside_exists= True`, `outside_content= ZIPSLIP-CONTROLLED-CONTENT`, and `inside_target_shadow_exists= False`. I also ran pdb non-interactively with a breakpoint at src/tools/visuals.py:1287; it printed the malicious `name`, the joined `dest`, and `dest.resolve(strict=False)` as `/tmp/pbi_mcp_zip_slip_owned.txt`, confirming the path traversal at the vulnerable write site. Crash/valgrind/ASan are not applicable because this is a Python logical arbitrary file write rather than a memory-safety crash.

    """Fallback PBIX extraction using the standard ZIP. Used when the bundled
    pbi-tools.core does not support 'extract' (it only ships 'compile').

    Copies the Report payload (Layout, StaticResources/Themes) so downstream
    layout-touching tools work. The data model stays inside the PBIX —
    consumers needing model definitions should rely on the live TOM
    connection via pbi_connect.
    """
    target.mkdir(parents=True, exist_ok=True)
    extracted: list[str] = []
    layout_path = target / LAYOUT_RELATIVE_PATH
    layout_path.parent.mkdir(parents=True, exist_ok=True)
    with zipfile.ZipFile(pbix, "r") as zf:
        names = set(zf.namelist())
        if "Report/Layout" in names:
            layout_path.write_bytes(zf.read("Report/Layout"))
            extracted.append("Report/Layout")
        # Copy theme JSONs so apply_theme / build_dashboard with theme references resolve.
        for name in names:
            if name.startswith("Report/StaticResources/") and not name.endswith("/"):
                dest = target / name
                dest.parent.mkdir(parents=True, exist_ok=True)
                dest.write_bytes(zf.read(name))
                extracted.append(name)

# Attack-path analysis

Final: high | Decider: model_decided | Matrix severity: medium | Policy adjusted: medium

## Rationale

Kept as high. The bug is real, in-scope, and reachable through the product's registered pbi_extract_report MCP tool. Static evidence shows the ZIP member name is selected by a simple Report/StaticResources/ prefix check and then written as target / name without resolving and checking containment. Earlier validation confirmed a malicious PBIX wrote /tmp/pbi_mcp_zip_slip_owned.txt outside the requested extraction folder. The default service is local/localhost and exploitation requires a malicious PBIX plus tool invocation and fallback behavior, which keeps it below critical. Nevertheless, arbitrary file write as the server user outside the path allowlist is a major integrity issue with credible same-user code execution/persistence paths, so high is appropriate.

## Likelihood

medium - The vulnerable code is exposed through a normal MCP tool and the PoC exercised that path. Exploitation is not unauthenticated internet-default: it requires tool invocation, a malicious PBIX in an allowed location, and fallback execution, while readonly/profile controls can disable the tool. These are plausible in the project's local AI-client threat model but not universally present.

## Impact

high - The vulnerable write occurs with the privileges of the MCP server's local OS user and bypasses the extraction-root/path-allowlist boundary. The validation evidence showed a crafted PBIX writing attacker-controlled content outside the requested extraction folder. Arbitrary write to user-writable startup, script, config, or project files can plausibly lead to same-user code execution or persistence; at minimum it enables significant local data corruption.

## Assumptions

- The server is run as the packaged FastMCP application via stdio or optional SSE.
- An attacker can influence an MCP client or user to process a malicious PBIX file located in an allowed local directory, or can otherwise invoke the pbi_extract_report tool with attacker-controlled PBIX content.
- The fallback path is used when pbi-tools is absent, lacks extract support, or reports success but does not leave Report/Layout in the extraction directory.
- pbi_extract_report is exposed by the selected server profile and not blocked by readonly policy
- attacker-controlled PBIX is available at a path accepted by resolve_local_path with .pbix extension
- native ZIP fallback executes because pbi-tools extraction is unavailable, unsupported, or ineffective
- server process has write permission to the traversal destination

## Narrative

The finding is valid and reachable in the main MCP server. pbi_extract_report is registered as a public MCP tool and validates only the user-supplied PBIX path and extraction folder. When the native ZIP fallback runs, it accepts any ZIP member starting with Report/StaticResources/ and writes it as target / name without canonicalizing the archive path or enforcing that the resolved destination remains under target. The provided validation PoC demonstrated normal tool invocation writing attacker-controlled bytes to /tmp outside the requested extraction folder. Default exposure is local/stdout or localhost SSE, and exploitation requires a malicious PBIX plus fallback execution, so this is not critical internet-scale exposure. However, it is an arbitrary local file write across the repository's intended path boundary with plausible same-user code execution or persistence by overwriting startup/config files, so high severity is justified.

## Controls

- Default stdio transport
- SSE binds to 127.0.0.1 by default
- Optional PBI_MCP_AUTH_TOKEN bearer authentication for SSE
- Readonly mode and profile-based tool pruning
- pbi_extract_report is classified as a write tool
- resolve_local_path path allowlist for explicit path parameters
- Symlink rejection for explicit local paths
- Audit logging with sanitized parameters

## Blindspots

- Static review did not enumerate all possible deployment profiles or operator-specific allowed directory configurations.
- No cloud/IaC artifacts were present to determine fleet exposure; default product exposure is local/stdout or localhost SSE.
- The exact prevalence of pbi-tools configurations that trigger fallback was not measured from repository artifacts, though the commit comments explicitly describe bundled pbi-tools.core lacking extract support.
- Specific Windows startup/config overwrite targets were not tested in this Linux container, but the arbitrary write primitive was validated.
