# Summary

Introduced. The new tool was added as a READ_TOOLS entry but performs write and UI side effects. It should not be exposed as a readonly tool, and screenshot/close behavior should require explicit write/UI-automation policy gating or a separate opt-in confirmation.
The commit adds pbi_validate_pbix_reopen to READ_TOOLS, so it is exposed under --profile readonly and allowed when --readonly blocks write/destructive tools. However, the implementation is not read-only: it starts a PBIX through PowerShell, optionally captures the entire primary screen to an attacker-supplied .png path within allowed directories, creates parent directories for that path, and optionally calls CloseMainWindow on the selected Power BI process. Because the PowerShell probe falls back to the first existing Power BI Desktop process if it cannot identify a new process, close_after can also close a pre-existing user session. A malicious prompt or MCP caller in a supposedly readonly deployment could therefore cause local file writes, privacy-sensitive screenshot capture, and UI/process disruption despite readonly controls.

# Attack-path analysis

Final: high | Decider: model_decided | Matrix severity: medium | Policy adjusted: medium

## Rationale

Kept at high. The repository evidence directly supports the core claim: the tool is classified and exposed as read-only while its implementation performs filesystem, screen-capture, process-start, and window-close side effects. In this project's threat model, malicious prompts or MCP callers are in scope and readonly policy is a central mitigation. Confidentiality impact can be high because CopyFromScreen captures the entire primary screen, not just Power BI. The issue is not raised to critical because exposure is local/localhost by default, execution is under the same OS user, a Windows interactive session is required, and the code shown writes the screenshot locally rather than directly returning or transmitting its contents.

## Likelihood

medium - The vulnerable tool is directly reachable through normal MCP operation and readonly/profile controls do not block it. However, practical exploitation requires a Windows interactive desktop, a valid allowed PBIX path, and attacker influence over MCP calls; default transport is stdio or localhost SSE rather than public internet.

## Impact

high - A read-only MCP deployment can be made to perform non-read actions: create directories, write a PNG screenshot of the entire primary desktop, and close a Power BI Desktop window that may predate the tool call. The screenshot can contain credentials, private business data, chats, or other applications outside Power BI. Integrity/availability effects are limited to local file creation and user-session disruption, and no RCE or privilege escalation is evidenced.

## Assumptions

- The server is used as intended on Windows with Power BI Desktop available.
- An attacker can influence MCP tool parameters through a malicious prompt, compromised MCP client, or reachable SSE client.
- Readonly mode or the readonly profile is relied upon by the operator to prevent filesystem writes, UI automation, and destructive/session-disrupting actions.
- No cloud APIs were queried; conclusions are based on repository artifacts and provided validation evidence.
- Windows runtime because the reopen probe is guarded by os.name == 'nt'
- Power BI Desktop installed or an existing PBIDesktop/pbidesktoprs process
- A PBIX path inside allowed local directories
- Ability to invoke MCP tool pbi_validate_pbix_reopen while server is in --readonly or --profile readonly
- Optional screenshot_path for screenshot write impact and/or close_after=true for UI/process disruption

## Narrative

The finding is real and reachable in the main MCP server. pbi_validate_pbix_reopen is explicitly registered as a read tool and included by --profile readonly, while readonly enforcement only blocks write/destructive categories. The public MCP wrapper accepts screenshot_path and close_after, then calls the implementation. On Windows, the implementation resolves attacker-supplied local paths, creates screenshot parent directories, runs a PowerShell probe that starts the PBIX and may fall back to an existing Power BI Desktop process, captures the entire primary screen to a PNG, and optionally closes the selected Power BI window. This violates readonly expectations and can expose sensitive desktop contents and disrupt the user's Power BI session. Severity remains high because confidentiality impact can be high, but it is not critical because the default exposure is local/localhost, it runs as the same OS user, and repository evidence does not show direct remote exfiltration of the PNG contents.

## Controls

- Default stdio transport
- SSE defaults to 127.0.0.1:8765
- Optional Bearer auth via PBI_MCP_AUTH_TOKEN for SSE
- --readonly runtime policy
- --profile readonly registry pruning
- Path allowlist defaults to current working directory or configured allowed_base_dirs
- Path traversal and symlink rejection in resolve_local_path
- PNG extension restriction for screenshot_path
- Windows platform guard for reopen validation
- Audit logging of tool calls with sensitive-value redaction
- Optional rate_limit_calls_per_minute policy; default is warning-only

## Blindspots

- Static-only assessment did not execute the real Windows PowerShell screen-capture path in this Linux container.
- Actual data exfiltration depends on the MCP client, local filesystem access, synced folders, or additional tools outside this specific code path.
- Operator-specific allowed_base_dirs and SSE binding/auth configuration are not known from repository artifacts.
- No cloud, Kubernetes, or load balancer manifests were present in the inspected evidence.
