# Summary

Introduced: the commit adds _ocr_reopen_screenshot and includes its full text output in the tool response, creating a new screen-text information disclosure path.
The commit adds optional Windows OCR to pbi_validate_pbix_reopen. When the caller supplies a screenshot_path, the existing reopen probe captures the entire primary screen, not just the Power BI Desktop window. The new OCR helper then recognizes text from that screenshot and returns the full OCR text in the windows_ocr response field. Because pbi_validate_pbix_reopen is classified as a read tool and the new use_windows_ocr parameter defaults to true, any MCP client that can invoke this read tool and point it at an allowed PBIX/screenshot path can exfiltrate visible text from other applications on the user's desktop, including documents, chats, emails, or secrets displayed on screen. The OCR result should not include raw text; it should only return bounded/redacted signals, crop to the Power BI window/canvas, and preferably be opt-in/default-off.

## Report

Validated the suspected OCR screen-text disclosure. I first attempted bounded dynamic reproduction rather than broad scanning. Crash reproduction is not applicable to this Python information-disclosure issue: running the PoC exited 0 (`crash_attempt_status.txt`: `exit_code=0`) and returned leaked text. Valgrind was attempted but unavailable in the container (`valgrind_attempt.log`: `valgrind unavailable in container; Python info-disclosure path is not a native memory-safety crash target`). I then used a non-interactive Python debugger trace.

Evidence:

1. The tool remains read-accessible: `src/security.py:21-43` lists `pbi_validate_pbix_reopen` among read tools, and policy code only blocks write/destructive categories in readonly mode (`src/security.py:363-383`, `401-410`). A targeted command confirmed `{'category': 'read', 'readonly': True, 'blocked': False}` for `pbi_validate_pbix_reopen` with `pbix_path` and `screenshot_path`.
2. The public MCP wrapper exposes `use_windows_ocr: bool = True` and forwards it (`src/server.py:627-646`). The implementation also defaults `use_windows_ocr=True` (`src/tools/quality.py:1354-1362`); `inspect.signature` confirmed this default.
3. When a screenshot path is supplied, the reopen probe captures the whole primary desktop, not a Power BI window crop: `src/tools/quality.py:1198-1205` uses `[System.Windows.Forms.Screen]::PrimaryScreen.Bounds` and `CopyFromScreen($bounds.Location, ..., $bounds.Size)`.
4. The newly added OCR helper returns raw recognized text: `src/tools/quality.py:1296-1336` assigns `$text = $result.Text` and serializes `{ text = $text, text_length = ..., matches = ... }`.
5. The tool returns that OCR object directly to the MCP caller: `src/tools/quality.py:1392-1409` calls `_ocr_reopen_screenshot(...)` when `use_windows_ocr` and `probe['screenshot_path']` are present, then returns `windows_ocr=ocr`.

Dynamic/debugger validation: `/workspace/validation_artifacts/powerbi-ocr-disclosure/poc_ocr_disclosure.py` creates a minimal valid PBIX-like zip, monkeypatches only Windows-only launch/OCR calls, omits `use_windows_ocr` so the real default is used, and calls the real `pbi_validate_pbix_reopen_tool` response assembly. `poc_output.json` shows `windows_ocr.text` contains `Personal chat: reset code 123456; AWS_SECRET_ACCESS_KEY=AKIA_TEST_EXFILTRATED`. The non-interactive pdb trace stopped at `quality.py:1392` and printed `use_windows_ocr` as `True`, the screenshot path as present, then after stepping over `_ocr_reopen_screenshot` printed the raw OCR object containing the same sensitive string; final response again included it under `windows_ocr.text`.

Limitation: the Linux container lacks PowerShell/Windows OCR/Power BI Desktop, so I could not perform a true end-to-end screen capture from the Windows desktop. However, the source code unambiguously captures the primary screen and serializes OCR `Text`, while the debugger-backed PoC proves the live Python tool returns raw OCR output to callers by default.

# Attack-path analysis

Final: high | Decider: model_decided | Matrix severity: medium | Policy adjusted: medium

## Rationale

Kept as high. The affected code is in the main MCP server runtime and is reachable through a registered public tool. Static evidence shows the tool is read-classified, OCR is default-on, screenshots capture the full primary desktop, raw OCR text is serialized, and the response returns it to the caller. The validation PoC also demonstrated sensitive text propagation through the real response assembly. The impact is major confidentiality exposure, but not critical because default exposure is local stdio/localhost SSE, optional auth exists for SSE, the attacker needs MCP tool access plus Windows/Power BI/screenshot preconditions, and the leak is limited to text currently visible on one user's desktop rather than broad unauthenticated remote compromise.

## Likelihood

medium - Exploitation is straightforward for any connected MCP client that can invoke read tools and provide allowed paths, and OCR is enabled by default. However, the service is local-first/localhost by default and requires a Windows Power BI Desktop environment plus sensitive text visible on the screen, so likelihood is medium rather than high.

## Impact

high - The bug can disclose raw text visible in other desktop applications, including documents, chats, email, reset codes, credentials, or API keys. This crosses the intended Power BI/read-tool boundary and can expose high-sensitivity data to an MCP caller.

## Assumptions

- The server is running on Windows with Power BI Desktop and Windows OCR available, because the affected tool explicitly rejects non-Windows execution.
- The attacker can cause an MCP-capable client or connected SSE client to invoke read tools, which is in scope for this local MCP server threat model.
- A valid PBIX path and allowed screenshot PNG path are available under the configured allowed base directory.
- Sensitive text is visible on the primary desktop at capture time.
- MCP tool-call access to the running server
- Windows host with Power BI Desktop workflow available
- caller supplies a valid allowed pbix_path
- caller supplies an allowed screenshot_path
- use_windows_ocr is not disabled or is explicitly true
- sensitive text is visible somewhere on the primary screen

## Narrative

The finding is a real, in-scope information disclosure. pbi_validate_pbix_reopen is registered as a public MCP tool and listed in READ_TOOLS, so readonly/profile controls do not block it. The public wrapper and implementation both default use_windows_ocr to true. If a caller supplies screenshot_path, the PowerShell probe captures the entire primary screen using System.Windows.Forms.Screen.PrimaryScreen.Bounds and CopyFromScreen. The OCR helper then serializes result.Text as text, and the tool returns the OCR object as windows_ocr. This lets a connected MCP client exfiltrate visible desktop text outside Power BI. Severity remains high because confidentiality impact can be significant, but it is not critical because the default deployment is local/localhost, requires MCP tool access, Windows/Power BI conditions, and visible sensitive data at capture time.

## Controls

- SSE binds to 127.0.0.1 by default
- Optional Bearer auth via PBI_MCP_AUTH_TOKEN for SSE
- Readonly and profile controls exist but classify the affected tool as read
- Path resolution enforces allowed base directories, extensions, length limits, and symlink rejection
- The affected reopen validation tool is Windows-only
- No default hard rate limit; only warning threshold unless configured

## Blindspots

- Static analysis cannot verify Windows OCR runtime behavior end-to-end in this Linux container.
- Actual exposure depends on operator deployment choices such as SSE host binding, PBI_MCP_AUTH_TOKEN, enabled tools, and allowed base directories.
- The amount and sensitivity of leaked data depends on what is visible on the user's primary desktop at the moment of capture.
- No Kubernetes, cloud, or load balancer manifests were present to prove internet exposure.
