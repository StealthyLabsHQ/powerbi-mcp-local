# Summary

Introduced authorization/profile bypass. The readonly profile is implemented as a static exposure filter over READ_TOOLS, but this commit added apply-capable write tools to READ_TOOLS. Those exposed tools can be switched into write mode at call time with apply=true and can perform model/report mutations under --profile readonly unless a separate readonly or deny-write security policy is configured.
The commit adds pbi_excel_import_workflow, pbi_measure_workflow, and pbi_repair_report_fields to both READ_TOOLS and WRITE_TOOLS, with tool_category() dynamically treating them as write only when apply is truthy. However, --profile readonly uses the static READ_TOOLS set to decide which MCP tools remain exposed and does not set the runtime readonly policy. As a result, a server launched with --profile readonly still exposes these tools. A client can call them with apply=true; validate_tool_call() will classify the call as write, but the default policy allows writes unless --readonly or an explicit deny-write policy is also configured. This bypasses the intended readonly profile boundary. The workflows then call mutating implementation functions directly: Excel import rewrites Power Query partitions and may refresh the model, measure workflow creates or updates measures, and report field repair writes the report Layout. The same design can also bypass fine-grained disabled_tools for the underlying primitives, because only the outer workflow tool name is checked by server._run().

def _apply_profile(profile: str) -> None:
    """Prune FastMCP's registered tools based on the selected profile."""
    if profile == "all":
        return
    from security import READ_TOOLS, WRITE_TOOLS, DESTRUCTIVE_TOOLS

    if profile == "readonly":
        allowed = set(READ_TOOLS)
    elif profile == "write":
        allowed = set(READ_TOOLS) | set(WRITE_TOOLS)
    else:
        return

    manager = getattr(mcp, "_tool_manager", None)
    tools_map = getattr(manager, "_tools", None)
    if tools_map is None:
        logger.warning("profile filter skipped: FastMCP tool registry not accessible")
        return
    removed = [name for name in list(tools_map.keys()) if name not in allowed]
    for name in removed:
        tools_map.pop(name, None)
    logger.info("PROFILE %s applied: removed %d tools, exposing %d", profile, len(removed), len(tools_map))

# Attack-path analysis

Final: high | Decider: model_decided | Matrix severity: medium | Policy adjusted: medium

## Rationale

Severity is retained as high. The code evidence and executable validation show the readonly profile boundary is bypassable: static profile pruning exposes dual-mode tools, runtime classification makes `apply=true` a write, and default policy allows writes unless `--readonly` or deny-write is separately configured. The reachable impact is unauthorized mutation of the user's Power BI model/report despite a read-only exposed surface, which is security-relevant in this MCP threat model where malicious prompts or clients are in scope. It is not raised to critical because the default exposure is local/stdio or localhost SSE, exploitation requires MCP access and a specific incomplete readonly configuration, and the demonstrated impact is local model/report integrity rather than RCE, broad public compromise, credential theft, or cross-tenant data tampering.

## Likelihood

medium - The bug is easy to trigger once an attacker can influence MCP tool calls, requiring only `apply=true` on exposed tools. However, it depends on the operator using `--profile readonly` without `--readonly` or deny-write policy, and the service is local/stdio or localhost SSE by default rather than broadly public.

## Impact

high - Successful exploitation allows a client that should only have read-only tool exposure to perform material local data/model/report writes: measure creation or overwrite, Power Query/Excel import and refresh, and report Layout modification. This is a high integrity impact on the primary project asset, though limited to the local/single-user Power BI environment rather than code execution or cross-tenant compromise.

## Assumptions

- The operator may reasonably launch the MCP server with `--profile readonly` to expose a read-only tool surface, as documented in README and CHANGELOG.
- An attacker can influence MCP tool calls through a connected MCP client, malicious prompt/tool-use flow, or an SSE client if SSE is enabled.
- The server runs with the same local OS user's access to Power BI Desktop files and local model/report state.
- Server is launched with `--profile readonly` without also enabling `--readonly` or an equivalent deny-write security policy
- Attacker can issue or influence MCP tool calls to the running server
- A Power BI model/report or extracted report folder is reachable to the server

## Narrative

The finding is a real in-scope authorization/profile bypass. `pbi_excel_import_workflow`, `pbi_measure_workflow`, and `pbi_repair_report_fields` are included in both `READ_TOOLS` and `WRITE_TOOLS`. The `--profile readonly` implementation prunes the registered MCP registry using only the static `READ_TOOLS` set, so those tools remain visible to clients. At call time, `tool_category()` classifies them as write when `apply` is truthy, but the default policy has `readonly=False` and `allow_write=True`; only the separate `--readonly` flag or explicit deny-write policy blocks the write. The server validates only the outer tool name before running the workflow, and the workflows call mutating primitives directly. The impact is unauthorized modification of a local Power BI model/report in a deployment that intended to expose read-only tools. This warrants high severity for integrity impact, but not critical because it is not public by default, requires MCP access and a specific incomplete readonly configuration, and does not demonstrate RCE, credential compromise, or cross-tenant impact.

## Controls

- Default transport is stdio
- SSE defaults to `127.0.0.1:8765`
- Optional SSE bearer authentication via `PBI_MCP_AUTH_TOKEN`
- Separate `--readonly` runtime policy blocks write/destructive categories
- Security policy supports `allow_write`, `allow_destructive`, `enabled_tools`, and `disabled_tools`
- Tool-call audit logging with sanitized parameters
- Profile pruning reduces exposed MCP registry but is not equivalent to runtime readonly enforcement

## Blindspots

- Static-only review did not exercise a real Power BI Desktop instance or confirm end-to-end model mutation in a live Windows environment.
- No cloud APIs were called and no deployment-specific SSE host/auth configuration was verified.
- The repository may be deployed with additional external controls, wrapper scripts, or policy files that always combine `--profile readonly` with `--readonly`, which would reduce practical exposure.
