# Summary

A security bug was introduced in the new allowlist enforcement: the newly added regex/literal-stripping logic does not cover valid M call syntax, so the advertised strict allowlist is bypassable. This does not remove the existing blocklist, but it undermines the new security guarantee that all non-allowlisted callable namespaces are rejected.
The commit adds a strict local-file allowlist for Power Query M function calls, but the validator is not a real M parser. It strips all double-quoted text as string literals, which also removes valid M quoted identifiers such as #"Python.Execute" or escaped quoted identifiers such as #"Web#(002e)Contents". It also only detects names immediately followed by '(', so disallowed functions used as first-class values and invoked through allowed higher-order functions can evade the allowlist. As a result, pbi_set_power_query can still accept M expressions that call functions outside the documented local-file allowlist, potentially enabling SSRF, external data access, or local script execution on refresh where those Power Query functions/connectors are available.

## Report

Validated. The project is Python, so crash/ASan/valgrind-style memory validation is not applicable to this logic bug; I used targeted dynamic PoCs plus a non-interactive Python debugger trace. The commit documents that Power Query calls are checked against a strict local-file allowlist and that any other callable namespace is rejected unless PBI_MCP_ALLOW_EXTERNAL_M=1. In src/tools/power_query.py, the allowlist detector is regex-based at line 85, strips all double-quoted text at lines 88-148, raises only for names matched by that regex at lines 151-164, is invoked from_validate_m_expression at lines 205-216, and pbi_set_power_query_tool sends user-controlled m_expression into that validator at lines 471-483. The PoC imported the real tools.power_query module and exercised both _validate_m_expression and pbi_set_power_query_tool with PBI_MCP_ALLOW_EXTERNAL_M unset. Control behavior worked: Csv.Document(File.Contents(...)) was accepted, and plain Python.Execute("print(1)") was rejected with disallowed_functions=['Python.Execute']. Bypass behavior was reproduced: #"Python.Execute"("print(1)") sanitized to '#                (          )', detected no function calls, and was ACCEPTED and written by pbi_set_power_query_tool. Value.Invoke(Python.Execute, {"print(1)"}) detected only ['Value.Invoke'] and was accepted/written. #"Web#(002e)Contents"("<http://127.0.0.1/>") also detected no calls and was accepted/written, showing an escaped quoted identifier can also evade the raw blocklist plus allowlist. Debugger trace confirmed the bypass path: _strip_m_literals_and_comments returned sanitized='#                (          )' with detected=[],_validate_m_function_allowlist returned disallowed=[], and_validate_m_expression returned without exception.

# Attack-path analysis

Final: high | Decider: model_decided | Matrix severity: medium | Policy adjusted: medium

## Rationale

Kept as high. The code evidence and executable helper PoC confirm a real allowlist bypass on the public pbi_set_power_query write path, not a test-only or documentation-only issue. The project explicitly treats external Power Query connectors as a security boundary, and the bypass allows documented-blocked M functions to be accepted while PBI_MCP_ALLOW_EXTERNAL_M is unset. This supports high impact due to credible SSRF/external data access and possible local script execution during refresh. It is not raised to critical because default exposure is local/localhost, the attacker needs MCP write-tool influence or a misexposed SSE endpoint, and the most severe effects depend on Power BI refresh behavior and connector/runtime availability.

## Likelihood

medium - The bypass payloads are simple and require no PBI_MCP_ALLOW_EXTERNAL_M opt-in, and the vulnerable code is on the normal pbi_set_power_query path. However, the default service is local/stdio or localhost SSE, and exploitation requires ability to invoke write tools, an active Power BI Desktop model, and refresh execution, so it is plausible but not broadly internet-exposed by default.

## Impact

high - A successful bypass lets a write-capable attacker place blocked M into the model and have Power BI evaluate it on refresh. This can enable SSRF to localhost/LAN/cloud metadata-like endpoints, external data access/exfiltration through connectors, or local script execution via functions such as Python.Execute where the user's Power BI environment supports them. The impact is constrained to the local user's Power BI/Desktop context and depends on refresh and connector availability.

## Assumptions

- A realistic attacker can influence MCP tool calls through an MCP client/prompt-injection path, or can reach the SSE transport if the operator exposes it.
- The target deployment has write tools enabled and is not running with --readonly or a policy disabling pbi_set_power_query.
- Power BI Desktop later evaluates the submitted M expression through refresh_after=true or a subsequent user/model refresh.
- The relevant Power Query connector or function, such as Web.Contents or Python.Execute, is available and permitted by the user's Power BI Desktop runtime.
- ability to cause an MCP write-tool call to pbi_set_power_query
- active or discoverable local Power BI Desktop session
- Power Query refresh of the modified partition
- dangerous Power Query function/connector available in the Power BI runtime

## Narrative

The finding is real and reachable. pbi_set_power_query is a registered MCP tool whose m_expression parameter flows into _validate_m_expression before being written to the model. The committed allowlist strips all double-quoted content and then applies a regex that only sees plain Name(...) calls. In Power Query M, #"..." is also valid quoted-identifier syntax, and disallowed functions can also be passed as first-class values to allowed Value.* functions. A helper-level executable PoC showed plain Python.Execute("print(1)") is rejected, while #"Python.Execute"("print(1)"), Value.Invoke(Python.Execute, {"print(1)"}), and #"Web#(002e)Contents"("<http://127.0.0.1/>") are accepted with PBI_MCP_ALLOW_EXTERNAL_M unset. Impact is high because this bypasses an explicit security boundary intended to prevent external data access, SSRF, and script-capable Power Query functions during refresh; it is not critical because default exposure is local/stdio or localhost SSE, write-tool access and refresh are required, and actual dangerous connector behavior depends on the user's Power BI runtime.

## Controls

- pbi_set_power_query is categorized as a write tool and can be blocked by --readonly or security policy.
- PBI_MCP_ALLOW_EXTERNAL_M defaults to 0, intending to block external/network M functions.
- Blocklist includes Web.*, database connectors, Expression.Evaluate, Value.NativeQuery, and #shared, but it is raw-regex based.
- Allowlist permits local import primitives and transformation namespaces, but enforcement is bypassable.
- SSE defaults to 127.0.0.1:8765; stdio is the default transport.
- SSE has no built-in authentication according to SECURITY.md.
- Rate limiting is policy-configurable but not enabled by default.

## Blindspots

- Static/container analysis could not run Windows Power BI Desktop to observe an actual Web.Contents request or Python.Execute execution during refresh.
- Connector availability, enterprise Power BI security prompts, privacy levels, and scripting configuration vary by deployment.
- The exact MCP client threat model and whether users expose SSE beyond localhost are deployment-specific.
- No cloud APIs were called; cloud/metadata SSRF impact is inferred from the ability to pass blocked network functions into Power Query.
