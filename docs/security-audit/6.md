# Summary

Introduced: new mutating MCP tools were registered and implemented, but omitted from the write tool category list. The existing fallback that treats unknown tool names as read turns the omission into a readonly/category-deny bypass.
The security gate classifies tools with tool_category() before execution. It blocks readonly mode only for tools categorized as write or destructive, and any tool missing from WRITE_TOOLS/DESTRUCTIVE_TOOLS falls through to read. This commit adds pbi_set_column_data_type, pbi_parameterize_data_source, pbi_relocate_data_source, and pbi_add_labelled_card, all of which perform writes when dry_run is false or mutate report layout, but the WRITE_TOOLS set was not updated. In the default --profile all mode, or when relying on --readonly/PBI_MCP_READONLY/deny write categories rather than profile pruning, an attacker who can influence MCP tool calls can still alter model column data types, rewrite Power Query partitions/data-source paths, create or update M parameters, and add visuals to extracted report layouts despite the operator intending a read-only deployment.

# Attack-path analysis

Final: high | Decider: model_decided | Matrix severity: medium | Policy adjusted: medium

## Rationale

Severity remains high. The bug is in the main runtime security gate, has executable PoC evidence, and bypasses an explicit readonly/deny-write authorization control for registered mutating tools. Although the default network exposure is local-only and this is not RCE or cross-tenant compromise, the project threat model centers on attacker-influenced MCP calls and relies on readonly policy to protect local Power BI assets. The proven impact is unauthorized integrity modification of the victim's model, Power Query definitions, and report layout.

## Likelihood

medium - The vulnerable path is straightforward once an attacker can influence MCP calls, and the default --profile all keeps these tools exposed. However, the server is local-first, stdio by default, and SSE defaults to localhost, so exploitation usually requires a malicious prompt/client or local/trusted-network access rather than broad internet reachability.

## Impact

high - A caller that should be limited to read-only operations can still modify Power BI model metadata, rewrite Power Query data-source expressions, create/update M parameters, request refreshes, or alter extracted report layouts. This directly violates the intended policy boundary and can compromise report/model integrity.

## Assumptions

- The operator intends a read-only deployment via --readonly, PBI_MCP_READONLY, or a policy that denies the write category while leaving the default --profile all tool surface available.
- An attacker can influence MCP tool calls through a connected MCP client, prompt injection, local stdio client, or SSE if exposed to the local host or a trusted network.
- The Power BI Desktop session or extracted report layout is accessible to the MCP server under the same OS user, which is the normal runtime model for this project.
- Server runs with the affected commit
- Readonly or deny-write category policy is relied on instead of --profile readonly pruning or explicit disabled_tools
- Attacker can cause or influence MCP calls to omitted mutating tool names
- A connected Power BI model or extracted report layout is available for mutation

## Narrative

This is a real in-scope authorization bypass. The central gate blocks readonly mode only when tool_category() returns write or destructive, but tool_category() returns read for unknown names. The new mutating tools are registered in the main MCP server and are not present in WRITE_TOOLS. Static evidence shows the omitted tools perform writes via execute_write or by composing existing layout-writing visual tools. The validation PoC also demonstrated that the omitted tools were allowed under readonly and that pbi_add_labelled_card changed a report Layout fixture from 0 to 2 visuals. Exposure is not public by default, so likelihood is medium rather than high, but the impact is high for deployments relying on readonly/deny-write as a security boundary against malicious MCP calls.

## Controls

- Default transport is stdio
- SSE default host is 127.0.0.1 on port 8765
- Optional SSE Bearer authentication via PBI_MCP_AUTH_TOKEN
- --readonly and PBI_MCP_READONLY enforce readonly based on tool_category()
- security_policy.json can set deny_categories, enabled_tools, or disabled_tools
- --profile readonly prunes tools to READ_TOOLS and mitigates these omitted names
- Optional rate_limit_calls_per_minute exists but is unset by default
- Path validation and allowed_base_dirs constrain file path parameters but do not fix the category bypass

## Blindspots

- Static review did not observe an actual deployed MCP client or operator configuration, so real-world reachability depends on how the server is launched.
- No cloud APIs were called and no live Power BI Desktop session was inspected during this attack-path review.
- Repository-only analysis cannot determine whether downstream packaging or runtime defaults add additional external exposure or compensating controls.
- The exact business impact of model/report mutations depends on the victim workbook/report and whether changes are later saved or published.
