# Summary

Introduced by this commit. The new mutating tools were registered in server.py and implemented in tools modules, but the security classification table was left unchanged. Since uncategorized tools default to read, the new write surface bypasses readonly/write-deny enforcement.
Central authorization depends on tool_category(): readonly and allow_write checks only block tools categorized as write or destructive, while unknown tool names fall through to read. This commit adds several tools that mutate the Power BI model or report layout, including time-intelligence/variance/contribution/top-N/rolling-average measure creation, format preset application, visual type conversion, and new scatter/combo/KPI/matrix visual creation. Because security.py was not updated, these new tool names are not in WRITE_TOOLS. The callbacks then directly call write helpers such as pbi_create_measures_tool, pbi_create_measure_tool, pbi_set_format_tool, or _save_layout without another policy check. In a deployment relying on --readonly, PBI_MCP_READONLY=1, or deny_categories=["write"], an MCP caller that should be limited to read operations can still create or update measures and modify extracted report layouts.

## Report

Validated the finding as a Python authorization logic bug. Key evidence: src/security.py:71-128 defines WRITE_TOOLS and omits the newly added mutating tool names; src/security.py:363-382 blocks readonly/allow_write only when tool_category() returns write/destructive; src/security.py:401-410 defaults unknown tools to read. Server dispatch then calls SECURITY.validate_tool_call() and immediately executes the callback at src/server.py:171-183, so a misclassified tool proceeds to its implementation. Dynamic PoC output showed legacy writes are blocked but new mutating tools are categorized as read: pbi_create_measure => write, pbi_add_card => write, but pbi_create_time_intelligence_pack, pbi_create_variance_measure, pbi_apply_format_preset, pbi_convert_visual_type, pbi_add_scatter_chart, pbi_add_combo_chart, pbi_add_kpi, and pbi_add_matrix all returned read. Under readonly, pbi_create_measure was blocked with 'Readonly mode blocks tool pbi_create_measure', while pbi_add_matrix was authorized. The PoC then called the real pbi_add_matrix_tool against a minimal extracted Report/Layout and verified mutation: before=0 after=1 response_ok=True visual_type=pivotTable. This confirms an MCP caller that passes central validation can modify report layout despite readonly. The same classification bypass was reproduced for deny_categories=[write]: pbi_create_measure was blocked, while pbi_apply_format_preset was allowed. Additional code evidence confirms other new tools are writes: pbi_add_matrix_tool builds projections and calls _append_visual at src/tools/visuals.py:2342-2412; _append_visual appends a visual container and _save_layout at src/tools/visuals.py:1078-1091; pbi_convert_visual_type saves modified layout at src/tools/visuals.py:1472-1480; DAX helpers delegate to manager.execute_write via pbi_create_measure_tool at src/tools/measures.py:64-125 and pbi_create_time_intelligence_pack_tool delegates to pbi_create_measures_tool at src/tools/measures.py:653-671; pbi_apply_format_preset_tool delegates to pbi_set_format_tool at src/tools/formats.py:152-178. Crash/valgrind are not applicable to this non-memory Python logic flaw; valgrind was not installed. I also ran the PoC under non-interactive pdb and it completed with the same bypass evidence.

        policy = self.policy()
        category = tool_category(tool_name, params)
        if policy.enabled_tools is not None and tool_name not in policy.enabled_tools:
            raise SecurityPolicyError(f"Tool '{tool_name}' is not enabled by the active security policy.")
        if tool_name in policy.disabled_tools:
            raise SecurityPolicyError(f"Tool '{tool_name}' is disabled by the active security policy.")
        if policy.readonly and category in {"write", "destructive"}:
            raise SecurityPolicyError(
                f"Readonly mode blocks tool '{tool_name}'.",
                details={"tool": tool_name, "category": category},
            )
        if category == "read" and not policy.allow_read:
            raise SecurityPolicyError(f"Read tools are disabled by the active security policy.")
        if category == "write" and not policy.allow_write:
            raise SecurityPolicyError(f"Write tools are disabled by the active security policy.")
        if category == "destructive" and not policy.allow_destructive:
            raise SecurityPolicyError(f"Destructive tools are disabled by the active security policy.")
        self._record_call(tool_name, policy)
        _validate_params(tool_name, params, policy)
        return policy

    def _record_call(self, tool_name: str, policy: SecurityPolicy) -> None:
        now = time.time()
        with self._lock:
            while self._calls and now - self._calls[0] > 60:
                self._calls.popleft()
            self._calls.append(now)
            count = len(self._calls)
        if policy.warn_after_calls_per_minute and count > policy.warn_after_calls_per_minute:
            self._logger.warning("SECURITY: high MCP tool call volume detected (%d calls/minute, latest=%s)", count, tool_name)
        if policy.rate_limit_calls_per_minute is not None and count > policy.rate_limit_calls_per_minute:
            raise SecurityPolicyError(
                "MCP tool call rate limit exceeded.",
                details={"count_last_minute": count, "limit": policy.rate_limit_calls_per_minute},
            )


def tool_category(tool_name: str, params: dict[str, Any] | None = None) -> str:
    if tool_name == "pbi_export_model" and params and not params.get("path"):
        return "read"
    if tool_name in {"pbi_excel_import_workflow", "pbi_measure_workflow", "pbi_repair_report_fields"}:
        return "write" if params and params.get("apply") else "read"
    if tool_name in DESTRUCTIVE_TOOLS:
        return "destructive"
    if tool_name in WRITE_TOOLS:
        return "write"
    return "read"

# Attack-path analysis

Final: high | Decider: model_decided | Matrix severity: medium | Policy adjusted: medium

## Rationale

Kept as high. The finding is not a false positive: repository code shows the new mutating tools are registered, omitted from WRITE_TOOLS, default-categorized as read, and routed to write sinks after central validation. It is in scope because the main threat model includes untrusted MCP tool parameters and readonly policy enforcement as the intended protection. The impact is a direct authorization bypass of read-only/write-deny policy with demonstrated model/report integrity consequences. It is not raised to critical because the product is local-first, defaults to stdio or localhost SSE, requires MCP-call reachability and an existing Power BI/report target, and does not demonstrate code execution, credential compromise, or broad remote unauthenticated exploitation.

## Likelihood

medium - Exploitation is straightforward once a caller can invoke MCP tools, and a prior executable PoC reportedly showed pbi_add_matrix authorized under readonly and mutating Layout JSON. However, exposure is commonly local/stdio or localhost SSE, and safe deployments using --profile readonly, disabled_tools, or an explicit enabled_tools allowlist are less affected.

## Impact

high - A caller intended to be read-only can perform meaningful state changes to Power BI artifacts: create/update DAX measures, apply measure/column formats, convert visual types, and add visual containers to report layouts. This undermines the project's primary safety boundary against prompt-injected or untrusted MCP calls. The impact is limited to the local user's Power BI model/report and does not show RCE, secret theft, cloud control-plane compromise, or cross-tenant impact.

## Assumptions

- The server is run with the default all profile plus --readonly, PBI_MCP_READONLY=1, or a policy such as deny_categories=["write"], rather than --profile readonly or an explicit enabled_tools allowlist.
- An MCP caller or prompt-injected AI client can request registered tools exposed by the server.
- For model mutations, Power BI Desktop/TOM is reachable; for layout mutations, the caller can reference a valid extracted report folder allowed by the normal path controls.
- MCP server exposes the new tools, normally via default --profile all
- Readonly/write-deny policy is relied upon for authorization
- Attacker-controlled or attacker-influenced MCP tool invocation
- Writable Power BI model or extracted report layout target exists

## Narrative

This is a real in-scope authorization bypass. The central dispatcher validates every MCP call, but validation depends on tool_category(). Newly registered tools that mutate measures, formats, and report layouts are not listed in WRITE_TOOLS, and uncategorized names default to read. As a result, readonly and deny-write policies authorize these tools and then execute callbacks that call write sinks such as manager.execute_write(), pbi_set_format_tool(), or _save_layout(). The impact is high-integrity compromise of a user's Power BI model/report under a policy that was explicitly intended to prevent such writes. It is not critical because the service is local-first, defaults to stdio or localhost SSE, and no RCE, cloud compromise, or broad unauthenticated internet exposure is shown.

## Controls

- Central SECURITY.validate_tool_call authorization
- READ_TOOLS, WRITE_TOOLS, and DESTRUCTIVE_TOOLS category sets
- --readonly flag and PBI_MCP_READONLY environment variable
- allow_categories and deny_categories security policy controls
- --profile readonly tool pruning mitigates if used
- Default stdio transport and localhost-only SSE host
- Optional SSE Bearer auth via PBI_MCP_AUTH_TOKEN
- Audit logging with parameter sanitization

## Blindspots

- This attack-path pass did not call cloud APIs or test a live Power BI Desktop/TOM session.
- Static review focused on listed tools and representative sinks; additional generated or future wrappers may have similar category drift.
- Actual exploitability depends on deployment profile, enabled/disabled tool policy, transport binding, and whether an MCP client can be influenced to invoke tools.
