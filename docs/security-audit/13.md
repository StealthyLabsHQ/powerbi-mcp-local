# Summary

A security regression was introduced. Replacing Path.cwd() with Path(__file__).parent makes the server ignore a restrictive security_policy.json in the working directory, defeating policy-based restrictions for deployments that follow the documented configuration.
The security policy loader is designed to load security_policy.json from the cwd argument it is given, and the project documentation states that security_policy.json in the working directory is a supported policy source. This commit changes server startup from Path.cwd() to Path(__file__).parent, so a policy placed next to the operator's launch/workspace directory is no longer loaded. If the operator relies on that policy for readonly mode, deny_categories, disabled_tools, max row limits, or allowed_base_dirs, the server falls back to permissive defaults: read/write/destructive tools are allowed and filesystem access defaults to the process CWD. Environment-based policy and the --readonly flag still work, but the documented working-directory policy path is bypassed for normal server startup.

## Report

Validated the finding as a Python logic/configuration security regression. Documentation says the server loads policy from `security_policy.json` in the working directory (SECURITY.md:204-208). The current commit changes startup to `SECURITY.policy(reload=True, cwd=Path(__file__).parent)` (src/server.py:1090-1091), while the loader resolves `(cwd or Path.cwd()) / "security_policy.json"` (src/security.py:219-237). Enforcement decisions for readonly/write/destructive/disabled tools depend on that loaded policy (src/security.py:296-315).

# Attack-path analysis

Final: high | Decider: model_decided | Matrix severity: medium | Policy adjusted: medium

## Rationale

Kept as high. The bug is in the main runtime startup path, contradicts documented policy loading, and directly disables the central authorization controls for deployments that use working-directory security_policy.json. The validation evidence shows normal server startup falls back to permissive defaults and allows a write tool that the documented policy would block. The issue is not critical because default exposure is local stdio/localhost, it requires an operator to rely on this policy source, and --readonly/PBI_MCP_READONLY/PBI_MCP_SECURITY_POLICY remain effective mitigations.

## Likelihood

medium - Exploitation requires a specific but plausible deployment pattern: the operator must rely on working-directory security_policy.json and the attacker must influence MCP calls. The server is not internet-facing by default and env/CLI mitigations still work, so likelihood is medium rather than high.

## Impact

high - A documented restrictive policy can be silently ignored, re-enabling write and destructive MCP tools and broadening filesystem access to default CWD behavior. In the project threat model, those tools can alter or delete Power BI measures, relationships, report pages/visuals, Power Query definitions, Excel workbooks, and model exports. This is materially security-relevant where policy is the intended boundary against malicious prompt/client-driven tool calls.

## Assumptions

- The operator relies on the documented working-directory security_policy.json rather than PBI_MCP_SECURITY_POLICY, PBI_MCP_READONLY, or --readonly.
- No security_policy.json exists beside src/server.py, so the changed startup path falls back to empty/default policy.
- An attacker can influence MCP tool calls through an MCP client, malicious prompt, local client compromise, or an exposed SSE endpoint.
- Server started normally from src/server.py or package entrypoint after the commit
- Restrictive policy is placed in the operator working directory
- Attacker can cause or send MCP tool calls
- Environment policy and CLI readonly mitigations are not used

## Narrative

The finding is real and reachable in the main product path. Documentation says security_policy.json in the working directory is a supported policy source, and tests exercise SecurityManager.policy(cwd=working_dir). The commit changed normal server startup to pass Path(__file__).parent, so the loader checks src/security_policy.json instead. If absent, it returns an empty mapping, creating a default policy that allows read, write, and destructive categories. Since every MCP tool wrapper calls SECURITY.validate_tool_call before execution, the incorrect policy source directly bypasses readonly, deny_categories, disabled_tools, row limits, and allowed_base_dirs that an operator placed in the documented working-directory policy. The impact is high for deployments relying on that policy, but not critical because the server is local-first, stdio/localhost by default, and environment policy or --readonly remain effective mitigations.

## Controls

- Default stdio transport
- SSE binds to 127.0.0.1 by default
- --readonly runtime flag still works
- PBI_MCP_READONLY environment variable still works
- PBI_MCP_SECURITY_POLICY JSON or absolute path still works
- Central SECURITY.validate_tool_call enforcement exists but is fed the wrong policy source for working-directory policies
- Path validation and symlink rejection remain present but depend partly on the active policy's allowed_base_dirs

## Blindspots

- Static repository review cannot measure how many real deployments use working-directory security_policy.json instead of environment policy or --readonly.
- No deployment manifests were present to prove internet or LAN exposure; exposure assessment is based on server CLI defaults and documentation.
- Runtime validation evidence used stubs for unavailable external MCP/Power BI dependencies, although the affected startup and policy code paths were exercised.
