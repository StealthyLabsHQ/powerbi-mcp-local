# Summary

Introduced: pbi_measure_dependencies was newly added in this commit and directly executes a blocked DMV query while being categorized as a read tool.
The commit adds pbi_measure_dependencies as a normal read tool and exposes it through the MCP server. Unlike pbi_execute_dax and pbi_trace_query, this tool does not call _validate_dax_query before running a DMV query. It hard-codes SELECT * FROM $SYSTEM.DISCOVER_CALC_DEPENDENCY and returns the resulting rows without redaction. This bypasses the repository's DMV policy gate, so a client operating under the default read-only/profile controls can still retrieve DMV metadata that the generic DAX execution path would reject. DISCOVER_CALC_DEPENDENCY can expose sensitive model internals and expression/dependency metadata, contrary to the intended PBI_MCP_ALLOW_DMV opt-in.

# Attack-path analysis

Final: high | Decider: model_decided | Matrix severity: medium | Policy adjusted: medium

## Rationale

Kept as high, not critical. Static evidence and the provided executable PoC support that the vulnerability is real: pbi_measure_dependencies is reachable as a READ MCP tool, skips the repository's DMV guard, directly executes $SYSTEM.DISCOVER_CALC_DEPENDENCY, and returns raw rows. The issue is in-scope because MCP client/tool-call influence and readonly/profile enforcement are central to the project's threat model. The impact is meaningful confidentiality loss and an explicit policy/authorization bypass for DMV metadata. However, it is not critical because the product is local-first, defaults to stdio or localhost SSE, requires an existing local Power BI Desktop session and MCP-call influence, and does not compromise credentials, execute code, or modify the model.

## Likelihood

medium - The vulnerable tool is registered and exposed in the read profile with no special parameters required, and prior validation showed it executes when PBI_MCP_ALLOW_DMV is unset. Exploitation still requires access to or influence over a local MCP client/server session and an open Power BI Desktop model, so it is not internet-wide by default.

## Impact

high - A read-only MCP caller can retrieve DMV/system dependency metadata and raw rows that the explicit policy gate is designed to withhold by default. The exposed data can include sensitive model internals, dependency relationships, object names, and expression metadata, but the issue is confidentiality-only and does not grant write access or code execution.

## Assumptions

- The MCP server is running with default DMV policy, so PBI_MCP_ALLOW_DMV is unset or not equal to 1.
- An attacker can influence or issue MCP read-tool calls through an MCP client, prompt-injection path, or configured SSE client.
- Power BI Desktop is open and the MCP server has a connected Analysis Services/ADOMD session.
- The operator has not explicitly disabled pbi_measure_dependencies in security_policy.json.
- MCP server process running
- Power BI Desktop model available to the same OS user
- attacker-controlled or attacker-influenced MCP tool invocation
- pbi_measure_dependencies exposed by the active profile or policy

## Narrative

The finding is real and reachable in the main product. The repository intentionally blocks $SYSTEM/DISCOVER DMV queries in _validate_dax_query unless PBI_MCP_ALLOW_DMV=1, and pbi_execute_dax_tool uses that guard. The new pbi_measure_dependencies endpoint is registered as an MCP tool and included in READ_TOOLS, so readonly/profile filtering exposes it to read-only clients. Its implementation bypasses _validate_dax_query, directly executes SELECT * FROM $SYSTEM.DISCOVER_CALC_DEPENDENCY, and returns raw rows. This is a confidentiality-focused policy bypass. It is not critical because the default deployment is local-first/stdio or localhost SSE, requires an open local Power BI Desktop session and MCP-call influence, and does not provide code execution or write access. It remains high in this project context because it defeats an explicit DMV opt-in security boundary and can disclose sensitive semantic-model dependency/expression metadata.

## Controls

- Default transport is stdio; optional SSE defaults to 127.0.0.1:8765.
- SSE bearer authentication is available when PBI_MCP_AUTH_TOKEN is set.
- Readonly mode and --profile readonly prune/block write and destructive tools, but pbi_measure_dependencies is categorized as read.
- The generic DAX path has a DMV guard controlled by PBI_MCP_ALLOW_DMV, but this tool bypasses it.
- max_rows_for_dax defaults to 5000, limiting but not preventing metadata disclosure.
- Tool calls are audited with parameter sanitization, but returned DMV rows are not redacted by this tool.

## Blindspots

- Static review did not query a live Power BI Desktop instance; exact DISCOVER_CALC_DEPENDENCY columns and sensitivity depend on the local Analysis Services version and model.
- No cloud APIs were called and no external deployment configuration was inspected.
- Reachability over non-local networks depends on operator choices such as --host and PBI_MCP_AUTH_TOKEN.
- Actual business impact depends on whether the user's model expressions/dependency metadata contain sensitive logic or secrets.
