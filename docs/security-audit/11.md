# Summary

A security bug was introduced. The refactor moved blocked-function checks from raw M text to sanitized text, but the sanitizer removes M quoted identifiers as if they were string literals. This creates a bypass for the external/network M function blocklist.
Power Query M supports quoted identifiers using #"...". This commit changed blocked-function checks to run on the output of strip_m_literals_and_comments(). That stripper treats every double-quoted sequence as a string literal and replaces its contents with spaces, without distinguishing ordinary strings from quoted identifiers. As a result, an expression such as `let Source = #"Web.Contents"("http://169.254.169.254/latest/meta-data/") in Source` is accepted by the validator even though it invokes the blocked Web.Contents function. The allowlist pass also misses the call because the function name has been stripped. Before this commit, the blocked-function regex was applied to the raw expression text, so the `Web.Contents` token inside the quoted identifier would still have been detected. This weakens the default PBI_MCP_ALLOW_EXTERNAL_M=0 protection and can allow SSRF or external database/network access when a malicious or prompt-injected MCP call writes an M expression and refreshes it.

# Attack-path analysis

Final: high | Decider: model_decided | Matrix severity: medium | Policy adjusted: medium

## Rationale

The original high severity is supported. The issue is in in-scope runtime product code, affects an exposed MCP write tool, and defeats a documented security boundary designed to prevent SSRF/external database/network access when PBI_MCP_ALLOW_EXTERNAL_M=0. Static review plus executable Python validation confirm the bypass: Web.Contents is rejected in raw form but accepted as #"Web.Contents" because the sanitizer strips the quoted identifier before blocklist/allowlist checks. The finding is not raised to critical because the server is local/stdio or localhost SSE by default, exploitation requires MCP write-tool reachability and a Power BI refresh, and no direct RCE, account takeover, or unauthenticated internet-wide path is shown.

## Likelihood

medium - The bypass is low-complexity once a caller can supply m_expression, and an executable validation PoC shows raw Web.Contents is rejected while #"Web.Contents" is accepted. However, exploitation usually requires local/authorized MCP tool access or prompt injection into an MCP client, write tools enabled, an open Power BI Desktop session, and a refresh, so default internet exposure is limited.

## Impact

high - A successful exploit bypasses the default external M connector block and can make Power BI Desktop issue attacker-chosen HTTP or database connector requests during refresh. This can expose internal services or cloud/LAN metadata reachable from the user's workstation and can mutate the model's data-source logic. It does not by itself prove arbitrary code execution or unauthenticated internet-wide compromise.

## Assumptions

- A realistic attacker can influence MCP tool calls through an MCP client, prompt injection, or an exposed SSE deployment.
- The server is running with write tools enabled and not in --readonly mode or a policy that disables pbi_set_power_query.
- Power BI Desktop is open and connected, and the written Power Query partition is refreshed either via refresh_after=true or a later pbi_refresh/manual refresh.
- Power Query M quoted identifiers of the form #"Name" are executable identifiers in the Power BI engine.
- access to invoke the pbi_set_power_query MCP write tool
- write/destructive policy not disabled and readonly mode not enabled
- running Power BI Desktop model connection
- table/partition target that can be modified
- refresh_after=true or a subsequent model/table refresh

## Narrative

This is a real, reachable product vulnerability. The committed runtime validator blocks Web.Contents and other external connectors, but first sanitizes the expression by stripping every double-quoted sequence. Power Query M quoted identifiers use #"...", so #"Web.Contents" is executable identifier syntax but is sanitized to spaces. The policy then checks only the sanitized text and misses both the blocklist and allowlist function-call checks. The exposed pbi_set_power_query MCP tool validates attacker-controlled m_expression and then writes it to a Power BI partition; refresh_after or pbi_refresh can trigger execution. Default transport is local/stdio or localhost SSE, so likelihood is not internet-wide by default, but the bypass defeats a security control specifically intended to prevent SSRF/external connector access from in-scope MCP write paths.

## Controls

- stdio transport is the default
- SSE binds to 127.0.0.1 by default
- pbi_set_power_query is classified as a write tool and can be blocked by --readonly or security policy
- PBI_MCP_ALLOW_EXTERNAL_M is an explicit opt-out and defaults to disabled
- M blocked-function and allowlist policy exists but is bypassed for quoted identifiers
- expression length validation is applied
- audit logging redacts sensitive-looking values

## Blindspots

- Static-only repository analysis could not execute Power BI Desktop or observe an actual outbound Web.Contents request during refresh.
- The exact behavior of Power Query privacy levels, credential prompts, and connector credential reuse depends on the victim's Power BI Desktop configuration.
- No deployment manifests were present to prove whether real users bind SSE beyond localhost or enable additional authentication/reverse proxies.
- The impact depends on what internal, LAN, or cloud metadata services are reachable from the user's workstation.
